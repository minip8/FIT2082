# M3

Rules and working notes for running this project on Monash's M3 cluster,
taken from the eResearch docs (https://docs.erc.monash.edu/Compute/HPC/M3/),
read 2026-10-09. The docs are the authority; check them again if something
here looks out of date.

## How Claude works with M3

Claude Code runs on the local machine and only sends short commands to M3 over
SSH. It never runs on M3 itself: the docs' "Don't run agents on the login
nodes" rule names agent tools ("like Cursor or Codex, as they can be resource
intensive"). An agent on M3 must go through the `M3_IDE`/`M3_Strudel` tunnels
below, so that it runs on a compute node.

Claude asks before its first `ssh`, `rsync` or `sbatch` in a session. M3 is a
shared external system, and a mistake there can cost the account its access.

On the login node, Claude only runs light commands:

- `sbatch`, `squeue`, `sacct`, `scancel`, `jobstats`, `mon_qos`, `show_cluster`,
  `user_info`, reading logs, small edits.
- Never training, QUANT transforms, tests or benchmarks. Those go in a job.
- **Never anything that downloads.** `uv sync` (several GB of torch/CUDA
  wheels), `git clone`, `scripts/fetch_datasets.py` and installs all go to an
  `M3_IDE` job or the data transfer node. An agent running on your own machine
  doesn't make a download on the login node acceptable. An M3 admin, on agents
  that run on login nodes: "they often download large files transparently.
  They also are inefficient as there are no GPUs on the login nodes. I kill any
  that I see".
- **Never poll faster than once a minute.** Loops that check the queue more
  often than that are banned. Prefer `sbatch --wait` or
  `--mail-type=END`, or check every few minutes at most.

What `M3_IDE` actually does (`/usr/local/sv2/ide_tunnel.sh`, read 2026-10-14;
the docs call the job "Remote", but the script names it `ide-tunnel`):

- If a RUNNING job named `ide-tunnel` exists, it connects to that job's node.
  Otherwise it runs `sbatch --job-name=ide-tunnel --nodes=1
  --ntasks-per-node=2 --time=04:00:00 --wrap='sleep 14400'`. That job has 2 CPUs,
  no GPU, the default partition (`comp`) and default memory.
- It waits 60 s for the job to start, then gives up ("Job failed to create
  within one minute"), **but leaves the job queued**. Each retry while the queue
  is busy submits another job, so check `squeue -u $USER -n ide-tunnel` and
  cancel any extra jobs.
- After 4 h the job ends and the session dies mid-command. The next connection
  starts a new job.
- When finished, run `scancel --name=ide-tunnel`. The job is only `sleep`, so
  an unused one just holds 2 cores.

## GPUs

- **Admins cancel jobs that reserve GPUs and leave them idle, without notice.**
  No threshold is published. Keep the GPU busy for the whole job. Run CPU-only
  stages, such as reading the memmap or a CPU QUANT pass, as a separate CPU job,
  or keep them short. Don't hold an interactive GPU session while nobody is
  using it.
- Request one GPU. HashBoost is single-GPU, and multi-GPU requests are only
  for code that has already saturated one GPU.
- Always request it explicitly (`#SBATCH --gres=gpu:1`). A job without
  `--gres` gets no GPU.
- Ask for the smallest GPU that fits. A less popular GPU often starts sooner and
  finishes sooner overall.
- After a run, check utilisation with `jobstats`. During a run, use
  `squeue -u $USER`, then `ssh <node>` and run `nvidia-smi` / `htop -u $USER`.

Partitions (`show_cluster` has the current list, `mon_qos` shows which QoS you
can use). As of 2026-10-14, `sinfo` shows no `m3g`, `m3i` or `m3m`, though the
docs still list them, and it shows L40S nodes, which the docs don't:

| Partition | GPUs | Notes |
|---|---|---|
| `gpu` | A100 (2/node), A40 (4), L40S (4, about 20 nodes), T4 (8) | pick one with `--gres=gpu:L40S:1` etc. |
| `m3h --qos=m3h` | H100 | 8 in total, in high demand |
| `fit --qos=fitq` | FIT GPU | access by application form |
| `comp` | none | default when `--partition` is omitted |

Use only restricted partitions the project has been granted. The error
"Invalid qos specification" means the QoS is missing or not granted.

## Resource requests

- Request only the CPUs, RAM and walltime the job uses. Extra cores don't speed
  up serial code. Extra RAM speeds nothing up, and exceeding the request
  triggers an OOM kill.
- Give the walltime a buffer and checkpoint so a killed job can resume.
- Always set the node count, and fill one node's cores before asking for
  another.
- Each task of an array job gets the full request.
- Interactive jobs: `smux` (recommended, because you can reconnect) or
  `srun --pty bash -i` from the login node.

## Storage

| Path | Quota | Backed up | For |
|---|---|---|---|
| `~` | 15 GB soft, 20 GB hard | yes | configs and keys only |
| `/projects/<proj>` | 500 GB | yes (scheme changing) | repo, job scripts, `results/` |
| `/scratch2/<proj>` | 3 TB, can be raised | **no** | `data/` (re-downloadable), intermediates |
| `/tmp` on a job node | node-local | no | deleted when the job ends |

- If you stay over the home soft limit for more than a week, writes are blocked.
  `user_info` shows the home quota. Quota increases go through
  https://tinyurl.com/massive-m3-quota-request (up to 2 weeks).
- Backups are nightly and kept for about 7 days. Report a deletion to the help
  desk at once, with the full path.
- `/scratch` is a leftover alias. Its filesystem (`/fs03`) was retired in
  April 2025, and the data moved to `/scratch2`. For our project,
  `/scratch/jt76 -> /fs03/jt76 -> /fs04/scratch2/jt76`, the same place as
  `/scratch2/jt76` (see `/scratch2/jt76/README.FS03_CUTOVER.20250402`). Always
  write `/scratch2/...` paths.
- `/scratch2` (`/fs04`) is Lustre: `df` shows it mounted from storage servers
  (`172.16.192.11`-`.18@o2ib`, over InfiniBand). It isn't stored on the login
  node or on any compute node. Every node is a client of the same filesystem,
  so a file written in one job is visible everywhere at once, and copying
  through the login node just loads that node as one more client.
  - Lustre is slow with many small files, because every open and stat goes to a
    shared metadata server. A torch venv has tens of thousands of them, so
    expect slower imports at job start than locally.
  - Large sequential reads (the MONSTER `.npy` memmaps) are what it's good at.
    The page-cache tuning in `stream_full.py` was measured on WSL and is
    unverified here.
  - A compute node's `/tmp` is a local disk, wiped when the job ends. For a job
    that reads many small files, copying them there first can help.
- Don't fill the small `/tmp` on the login and dtn nodes.
- Transfer data through the data transfer node (dtn), not the login node, using
  `rsync`/`scp`, Globus, FileZilla or similar. The host is
  `m3-dtn.massive.org.au` (`M3_DTN` in `~/.ssh/config`; it resolves to
  `m3-dtn1`/`m3-dtn2`, with 64 cores and 1 TB RAM). Its host key is the same
  ED25519 key as the login nodes, checked from both outside and inside M3.

## Running jobs

`scripts/m3_job.sh` wraps a repo command as a GPU job. Submit it from the repo
root on M3, with `sbatch` flags before the script to override its defaults
(1 L40S, 4 CPUs, 32 GB, 1 h):

    sbatch scripts/m3_job.sh python -m fit2082.boost.experiment --dataset Pedestrian ...
    sbatch --time=04:00:00 --mem=64G -J lendb scripts/m3_job.sh python scripts/stream_full.py ...

It runs the command under `uv run --no-sync`, keeps torch's compile cache on
`/scratch2` so later jobs skip recompiling, and logs to
`/scratch2/jt76/myan0101/logs/<name>-<id>.out`. The log starts with node, GPU,
commit and command, and ends with the exit status and mean GPU utilisation
(sampled every 10 s into a `.gpu.csv` beside it), because `jobstats` crashes on
our jobs.

Keeping the M3 checkout current: push the code with `rsync` through `M3_DTN`,
with `--no-g` so new files take the directory's `jt76` group:

    rsync -a --no-g --exclude=/data/ --exclude=/results/ --exclude=.venv/ \
        --exclude=__pycache__/ --exclude=.pytest_cache/ --exclude=.ruff_cache/ \
        ./ M3_DTN:/projects/jt76/myan0101/fit2082/

Then pull results back with
`rsync -a --ignore-existing M3_DTN:/projects/jt76/myan0101/fit2082/results/ results/`.

## Python environment

The venv is a directory on a shared filesystem, which every node mounts, so it
outlives any one job. Run `uv sync` once, then again only when `uv.lock`
changes (after a `git pull`). Even then uv fetches only the changed packages, as
long as its cache is still there.

Set in `~/.bashrc.d/fit2082.sh` on M3 (the stock `~/.bashrc` sources
`~/.bashrc.d/*`), and sourced at the top of every job script:

    export UV_CACHE_DIR=/scratch2/jt76/myan0101/uv-cache
    export UV_PROJECT_ENVIRONMENT=/scratch2/jt76/myan0101/venvs/fit2082
    export UV_PYTHON_INSTALL_DIR=/scratch2/jt76/myan0101/uv-python
    module load uv

- **The cache goes on `/scratch2`, not in `~/.cache/uv`.** torch with CUDA is
  several GB, and the home quota is 15 GB.
- **The venv goes on `/scratch2` too.** It can be regenerated, so the lack of
  backups doesn't matter, and `/projects/jt76` is shared and nearly full. On
  the same filesystem as the cache, uv hardlinks files instead of copying them,
  so they aren't stored twice.
- **`uv sync` runs only on a compute node**, never on the login node (see
  above). A CPU batch job beats an `M3_IDE` session for this: it ends when the
  sync does, and `sbatch --wait` reports completion without polling:

      sbatch --wait -p comp -J uv-sync -n 1 -c 4 --mem=16G -t 01:00:00 \
          -o /scratch2/jt76/myan0101/logs/%x-%j.out \
          --wrap "source ~/.bashrc.d/fit2082.sh; cd /projects/jt76/myan0101/fit2082 && uv sync --frozen"

  First sync (job 61002438, 2026-10-14) took 48 s and installed Python 3.12.12
  and torch 2.13.0+cu130. The venv is 5.9 GB, and the cache adds only 26 MB
  beyond it because the two share files through hardlinks. cu130 needs an
  NVIDIA driver >= 580 on the GPU nodes. The first GPU job had 580.126.20.

Smoke test (job 61002609, 2026-10-14, `--gres=gpu:1` landed on a T4 on
`m3t100`; script in `/scratch2/jt76/myan0101/logs/smoke.sh`): 4:00 elapsed of a
10 min limit.

- `import torch` from the Lustre venv took 15 s per process.
- `experiment.py --dataset Pedestrian --seeds 1 --compile --variants baseline`
  took 74 s in all. Its reported wall was 32.5 s (one seed: val error 0.2295),
  against 8-14 s on the local RTX 4060, so a T4 is the slow choice. Name the
  GPU (`--gres=gpu:L40S:1`, `gpu:A100:1`) when speed matters.
- `pytest`: 214 passed in 142 s, with the CUDA tests running. The slowest test
  is `test_compiled_pulsar_agrees_with_eager_at_the_tie_level` (43 s). Keep
  pytest out of real jobs, because the GPU is mostly idle during it.
- `jobstats <id>` crashed with a `TypeError` in its own formatter on this job.
  `sacct -j <id> -o JobID,State,Elapsed,AllocTRES` works.
- **Jobs use `uv run --no-sync`** (or export `UV_NO_SYNC=1`). Otherwise `uv run`
  silently re-syncs after a lock change, so every job, or a stray command on
  the login node, would start downloading. With `--no-sync`, syncing happens
  only when someone runs `uv sync` deliberately.
- `UV_PYTHON_INSTALL_DIR` matters because uv also downloads Python 3.12, which
  otherwise lands in `~/.local/share/uv`.
