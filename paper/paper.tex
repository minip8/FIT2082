\begin{abstract}
    On large time series datasets, training the classifier becomes the
    expensive part of classification. A boosted tree ensemble such as XGBoost
    searches every feature for splits in every round, so its cost grows with
    the size of the data, and it must hold the whole training set. We replace the tree with a \emph{global partition}: a few threshold
    predicates, placed between pairs of hard, differently labelled examples,
    that index a table of leaf values. The resulting booster, HashBoost,
    trains from mini-batches on the GPU. Its cost is set by its round budget
    rather than by the size of the data, and its memory does not grow with
    the training set. We evaluate it on MONSTER, a benchmark of 26 large time
    series datasets, using QUANT features. With both models tuned by the same
    procedure and scored on the official test folds, HashBoost matches tuned
    XGBoost's accuracy and trains 8.2$\times$ faster in total on the same GPU: up to 31$\times$ faster on
    the datasets where XGBoost is most expensive, though slower on the
    cheapest. On the small datasets of the UCR archive the advantage
    disappears: QUANT's own ExtraTrees classifier is both faster and more
    accurate there.
\end{abstract}

\section{Introduction}

Gradient boosted decision trees~\cite{friedman2001greedy}, in implementations
such as XGBoost~\cite{chen2016xgboost}, LightGBM~\cite{ke2017lightgbm} and
CatBoost~\cite{prokhorenkova2018catboost}, are the default choice for tabular
prediction, where they remain competitive with, and frequently superior to,
deep learning~\cite{shwartzziv2022tabular,grinsztajn2022why}. Tree ensembles
are also the usual classifier on top of interval-based time series features:
QUANT~\cite{dempster2024quant} passes its quantile features to extremely
randomised trees, and PULSAR~\cite{pulsar} is used the same way.

At the scale of the MONSTER
benchmark~\cite{dempster2025monstermonashscalabletime}, with up to 5.9 million
series per dataset and tens of thousands of features after QUANT, the
classifier becomes the expensive part. To grow a boosted tree, the learner
searches for split points on every feature, and a multiclass booster grows one
tree per class per round. Each round therefore costs time in proportion to rows,
features and classes together. Histogram binning, approximate split finding,
gradient-based sampling and feature
bundling~\cite{chen2016xgboost,ke2017lightgbm,friedman2002stochastic} reduce
the constant factor, but every round must still revisit the whole training
set and hold it in memory.

This paper replaces each tree with a \emph{global partition} of the feature
space: $b$ axis-aligned threshold predicates, applied to every example at
once, whose $b$ bits index a table of $2^b$ leaf values. A predicate takes a
random feature and puts its threshold at the midpoint of two hard, differently
labelled examples, so there is no search over the training set. Each leaf value
is a Newton step computed from running sums of the gradient and hessian.
Because the partition does not depend on which examples are in the current
batch, those sums can be updated from any later mini-batch, and the model never
needs the training set in one place. Its training cost is set by how many
rounds and batches it is given, not by how large the data is.

Our claim is that this booster matches tuned XGBoost's accuracy on large-scale
time series classification, and that because its cost does not grow with the
data, it trains far faster exactly where XGBoost is most expensive. We ask:
\begin{description}
    \item[RQ1] Given the same tuning effort, does HashBoost match a tuned
               boosted tree ensemble's accuracy on MONSTER's test folds?
    \item[RQ2] How much faster is it, on which datasets, and why? What does
               each model reach in the same training time, and what memory
               does each need?
    \item[RQ3] Where does the advantage stop? We test the small training sets
               of the UCR archive.
\end{description}

\paragraph{Contributions.}
\begin{enumerate}
    \item \textbf{HashBoost}, a gradient booster whose weak learner is a global
          partition. Round freezing makes its training cost linear in the
          number of rounds, and its GPU implementation agrees with an
          independent CPU reference to $4\times10^{-7}$ (\cref{sec:method}).
    \item \textbf{A test-fold comparison on all 26 MONSTER datasets} against
          XGBoost tuned by the same procedure and against QUANT's ExtraTrees,
          trained on whole pools of up to 4.65 million rows
          (\cref{sec:accuracy}).
    \item \textbf{An account of where the time goes}: per-dataset speedups
          explained by XGBoost's cost per round, a time-matched comparison, and
          memory against training-set size (\cref{sec:cost}).
    \item \textbf{The small-data boundary} on the 112 UCR datasets
          (\cref{sec:ucr}).
\end{enumerate}

Our code is available at \url{https://github.com/minip8/FIT2082}.

\section{Background and Related Work}
\label{sec:related}

\paragraph{Boosting.}
Boosting combines weak learners into a strong one, as formalised by
AdaBoost~\cite{freund1997decision} and generalised to differentiable losses as
gradient boosting~\cite{friedman2001greedy}. Trees are the conventional weak
learner, but nothing in the framework requires them. Modern implementations fit
each tree to a second-order expansion of the loss, so that a leaf's value is a
Newton step $-\sum g / \sum h$ over its examples~\cite{chen2016xgboost}.
HashBoost keeps this leaf rule and changes how examples are assigned to leaves.

\paragraph{Oblivious trees and decision tables.}
CatBoost~\cite{prokhorenkova2018catboost} grows \emph{oblivious} trees, in
which every node at a given depth uses the same split, so a depth-$d$ tree is
$d$ predicates indexing $2^d$ leaves. This is the structure of one HashBoost
round, and neural oblivious ensembles~\cite{popov2020node} use it too. CatBoost
chooses each level's split greedily by gain over the whole training set and
fixes the leaves once the tree is built. Boosted decision
tables~\cite{lou2017bdt} are the closest relative. They choose a table's tests
greedily by gain over the whole training set, then \emph{backfit} them,
re-choosing each test given the others. Their leaves are set once, and earlier
tables are never revisited. HashBoost does the opposite on both counts. Its
tests are not searched for over the training set, and every earlier round's
leaves are re-estimated by each later batch. That is closer to backfitting
additive models~\cite{buja1989linear}, applied online.

\paragraph{Randomised partitions.}
Random forests~\cite{breiman2001random} and extremely randomised
trees~\cite{geurts2006extremely} showed that much of a tree's split search can
be replaced by randomness, provided the ensemble is large. A random global
partition can also be read as a locality-sensitive
hash~\cite{indyk1998approximate}: examples that share a code agree on $b$
random comparisons. HashBoost's thresholds are random but not uninformed. They
sit between two hard examples of different classes, so each bit tends to
separate examples the current model confuses.

\paragraph{Scaling and streaming.}
The usual way to make tree boosting fast at scale is to keep the search and
accelerate it. GPU histogram construction~\cite{mitchell2017accelerating}
builds each tree's histograms in parallel, and out-of-core
training~\cite{chen2016xgboost} pages the binned matrix from disk. Both still
pass over the whole training set every round. Learning from a stream is the
other route. Hoeffding trees~\cite{domingos2000mining} grow one tree from a
stream, splitting a leaf once enough examples have arrived to choose its test
with confidence, and online boosting~\cite{oza2001online,beygelzimer2015online}
updates every weak learner as each example arrives. HashBoost is closest to
online boosting: it updates all existing learners from each new batch. Unlike
online boosting, its learners' structure is fixed when they are created, so an
update is a scatter-add rather than a refit.

\paragraph{Time series classification.}
Random-feature methods have shown that data-dependent search can often be
replaced by cheap random transformations: ROCKET~\cite{dempster2020rocket},
MiniRocket~\cite{dempster2021minirocket} and Hydra~\cite{dempster2023hydra}
pair random convolutional kernels with a linear classifier, at a fraction of
the cost of ensembles such as HIVE-COTE~\cite{middlehurst2021hivecote2}.
Interval methods (Time Series Forest~\cite{deng2013tsf},
CIF~\cite{middlehurst2020cif}, DrCIF~\cite{middlehurst2021hivecote2},
rSTSF~\cite{cabello2021rstsf}, QUANT~\cite{dempster2024quant},
PULSAR~\cite{pulsar}) all end in some form of tree. We keep QUANT as a fixed
transform and replace only the classifier.

\section{Method}
\label{sec:method}

\subsection{A round is a global partition}

Let $x \in \mathbb{R}^p$ be a feature vector and $k$ the number of classes. A
round $r$ is defined by $b$ pairs $(j_{r,i}, t_{r,i})$ of a feature index and a
threshold, for $i = 0, \dots, b-1$. It maps $x$ to a $b$-bit code
\begin{equation}
    c_r(x) = \sum_{i=0}^{b-1} 2^i \, \mathbb{1}\!\left[x_{j_{r,i}} \le t_{r,i}\right]
    \in \{0, \dots, 2^b - 1\},
\end{equation}
and has a table $L_r \in \mathbb{R}^{2^b \times k}$ of leaf values. The model
after $R$ rounds is
\begin{equation}
    F(x) = \sum_{r=1}^{R} L_r\!\left[c_r(x)\right] \in \mathbb{R}^k,
\end{equation}
and predicts $\mathrm{softmax}(F(x))$. A round is an oblivious tree of depth
$b$ whose splits are fixed when it is created. The default is $b = 8$, so a
round has 256 buckets.

\subsection{Choosing the predicates}

Given the current batch, its labels and the model's predicted probabilities,
a new round's predicates are chosen as follows:
\begin{enumerate}
    \item Order the batch by cross entropy, hardest first.
    \item Walk that order and greedily form $b$ pairs of examples with
          different labels.
    \item For each pair $(u, v)$, draw a feature $j$ uniformly at random and set
          $t = (u_j + v_j)/2$.
\end{enumerate}
Each bit therefore separates two examples the model currently gets wrong, and
the only search is the sort in the first step. A \emph{gain-selected} variant
draws a pool of $bK$ such hard-pair candidates and fills the bits one at a
time, the way CatBoost grows an oblivious tree level by level
(\cref{sec:related}): each bit takes the unused candidate
with the highest second-order gain, $\sum G^2/(H+\lambda)$ with $\lambda = 1$,
summed over classes and over the cells the earlier bits have made. Here $G$
and $H$ are the batch's gradient and hessian summed within a cell. Unlike
CatBoost, it scores only these $bK$ random candidates, on one batch, rather
than every feature over the whole training set.

\subsection{Fitting the leaves}
\label{sec:leaves}

We use the softmax cross-entropy gradient $g = p - \mathrm{onehot}(y)$ and a
floored diagonal hessian $h = p(1-p) + 10^{-3}$. Every round keeps running sums
$G_r, H_r \in \mathbb{R}^{2^b \times k}$ of $-g$ and $h$ over the examples that
landed in each bucket, and its leaf values are
\begin{equation}
    L_r[s] = \eta \, \frac{G_r[s]}{H_r[s] + \epsilon},
\end{equation}
with learning rate $\eta = 0.1$. By default $\epsilon = 10^{-6}$; a larger
$\epsilon$ is an L2 penalty that shrinks thinly populated leaves.

The key departure from tree boosting is \emph{when} these sums are
accumulated. A tree's leaves are fitted once and never change. In HashBoost,
\textbf{every mini-batch is accumulated into every existing round}, with
gradients evaluated at the current model (\cref{alg:hashboost}). A round
created early keeps absorbing evidence from every later batch, so it is not
tied to the batch that created it, and the model can learn from a stream.
Adding $M > 1$ rounds per batch raises capacity without more passes over the
data.

\begin{algorithm}[t]
    \caption{One HashBoost step on a mini-batch $(X, y)$ of $n$ examples,
        adding $M$ rounds.}
    \label{alg:hashboost}
    \begin{algorithmic}[1]
        \For{$m = 1, \dots, M$}
        \State $F \gets \sum_{r=1}^{R} L_r[c_r(X)]$ \Comment{$(n, k)$ logits}
        \State $p \gets \mathrm{softmax}(F)$;\quad $g \gets p - \mathrm{onehot}(y)$;\quad $h \gets p(1-p) + 10^{-3}$
        \State choose predicates of round $R+1$ from hard pairs in $(X, y, p)$
        \For{$r = 1, \dots, R+1$} \Comment{all rounds, including the new one}
        \State $G_r[c_r(X)] \mathrel{+}= -g$;\quad $H_r[c_r(X)] \mathrel{+}= h$ \Comment{scatter-add}
        \State $L_r \gets \eta\, G_r / (H_r + \epsilon)$
        \EndFor
        \State $R \gets R + 1$
        \EndFor
    \end{algorithmic}
\end{algorithm}

\subsection{What training costs}
\label{sec:freezing}

A batch of $n$ rows costs encoding and scatter-adds over the rounds it
touches, $O(nRb + nRk)$, plus choosing its new predicates on that batch alone.
Nothing in this depends on the size $N$ of the training pool. Total cost is the
number of batches times the cost per batch, and memory holds only one batch and
the tables. A boosted tree's round instead builds feature histograms over all $N$
rows, for each of the $k$ class trees, so its cost per round grows with $N
\cdot p \cdot k$, and it needs the binned matrix of all $N \times p$ values.

HashBoost has a scaling problem of its own. Because every batch updates every
round, a batch costs $O(R)$ once there are $R$ rounds, so $T$ batches cost
$O(T^2)$. \emph{Round freezing} removes this growth. With a window of $W$ rounds, only the newest $W$ keep accumulating, and a
frozen round's contribution to an example never changes again. Given stable
row ids, each row's frozen contribution is summed once and cached in an
$(N, k)$ table. A batch then costs $O(W + f)$, where $f$ is the number of
rounds frozen since its rows were last seen, and total cost becomes linear in
rounds.

\subsection{Implementation}
\label{sec:implementation}

HashBoost runs entirely on the GPU in PyTorch. The original numba CPU
implementation is kept as a reference: given the same predicates, the two agree
to $4\times10^{-7}$ in logits with identical predictions. The GPU version trains Pedestrian's default 800 rounds in about 7.5\,s,
against 101.5\,s for the reference.

The code is organised so that an experiment can change one component at a
time. The predicate family, the split selector and the loss are separate
interfaces (Python \code{Protocol}s), and every experimental change is an
opt-in option, so the default model stays the reference algorithm. On the GPU
the greedy pairing of hard examples runs as a single Triton kernel, so a round
needs no transfer back to the host, and a test checks that it chooses the same
pairs as the Python version. The 224 tests also cover the QUANT port against
its upstream reference. Every run writes its results to a file named after
its commit, so every number here can be traced to the code that produced it.

\paragraph{Configurations.}
\label{sec:configs}
HashBoost and XGBoost were tuned the same way, on fold 0's validation error
alone. We screened one change at a time on 10 of the 26 datasets
(CrowdSourced, DREAMERA, FordChallenge, InsectSound, LenDB, PAMAP2, STEW,
Traffic, UCIActivity and WISDM), fixed two configurations per model, and ran
both on all 26. For each dataset and model the configuration with the lower
fold-0 tune error was frozen. Each frozen configuration was then trained once
on each of the five folds and scored once on that fold's test series, at the
round its tune error chose. No test series was seen before this.

Both HashBoost configurations train for up to 5,000 batches of 4,096 rows,
evaluate every 50 batches, stop once their best tune evaluation is 1,000
batches old, and freeze rounds older than 128 batches:
\begin{itemize}
    \item \code{G}: 6-bit gain-selected rounds ($K = 64$, so a pool of 384 candidates),
          $\epsilon = 100$, 8 rounds per batch. Picked on 18 datasets.
    \item \code{L}: 8-bit hard-pair rounds, $\epsilon = 1$, 16 rounds per
          batch. Picked on the largest pools (LenDB, both S2Agri, Traffic,
          Pedestrian), WhaleSounds and the EEG sets DREAMERA and DREAMERV.
\end{itemize}
Gain selection had not helped on 65,536-row slices, but on whole pools, with
6-bit rounds and a heavy leaf penalty, it was the largest single gain in the
screen (CrowdSourced's validation error fell from 0.042 to 0.006). Over five
model seeds on fold 0, the same configuration was picked every time on 25 of
the 26 datasets.

We compare against one tree booster, tuned with the same effort as HashBoost:
XGBoost, because it trains on the same GPU, so the times compare directly, and
can train out of core (\cref{sec:memory}). On early 65,536-row slices,
LightGBM's validation error was in the same range. XGBoost's screen raised its cap to 5,000 rounds with 100 rounds of patience,
then varied depth, learning rate, subsampling, L2 regularisation and the
number of bins. Its configurations are \code{d4} (depth 4, learning rate 0.1;
picked on 17 datasets) and \code{d8} (depth 8, learning rate 0.05, 64 bins;
picked on 9). The third model, ExtraTrees with QUANT's own settings (200 trees,
entropy criterion, a tenth of the features per split), chooses nothing after
training, so it trains on the same rows and needs no tune slice.

\paragraph{UCR.}
For the small-data boundary we use the 112 univariate UCR
datasets~\cite{dau2019ucr} that the bake-off reports
on~\cite{middlehurst2024bakeoff}: the archive's 128, less the 15 with missing
values or unequal lengths and Fungi, which has one training series per class.
Each is used on its default train/test split. The training sets have 16 to 8,926 series (median 190). There is no validation split, so
every model runs at fixed settings and we report test error: HashBoost at 800
rounds of 8 bits, ExtraTrees with QUANT's settings, and XGBoost at its library
defaults (100 rounds, learning rate 0.3, depth 6).

\paragraph{Hardware and timing.}
Every HashBoost and XGBoost run on MONSTER had one NVIDIA L40S (46\,GB) on
Monash's M3 cluster to itself, so their times are directly comparable. ExtraTrees ran on
CPU nodes with 36 cores, and its time is not. Training time includes the QUANT
transform for both boosters. UCR and the streaming runs in
\cref{sec:memory} used one RTX 4060 (8\,GB). Seeding does not make HashBoost
reproducible, because float32 scatter-adds on the GPU accumulate in a
nondeterministic order. On Pedestrian the run-to-run standard deviation of
validation error is about 0.003.

\paragraph{HashBoost matches tuned XGBoost.}
HashBoost's error is 1.016 times XGBoost's in geometric mean. It is lower on
14 datasets and higher on 12, and lower on 61 of the 130 dataset-folds. The
Wilcoxon test finds no difference ($p = 0.98$). A non-significant test alone
does not show that two models are equal, so we also bound the gap: a 95\%
$t$-interval over the 26 datasets' log error ratios gives a geometric-mean
ratio between 0.97 and 1.07, so on average neither model's error is more than
about 7\% above the other's\footnote{\label{fn:wisdm}One

Counting the failed run, the ratio is 0.992 ($p = 0.71$).}. Where one model clearly leads, it is usually XGBoost: on

only on AudioMNIST-DS. The 10 tuning datasets flatter HashBoost, which was
developed on them for much longer than XGBoost was tuned: its ratio there is
0.973, against 1.045 on the other 16.

\paragraph{Both boosters rank ahead of ExtraTrees.}
The mean ranks are 1.77 for both boosters and 2.46 for ExtraTrees
(\cref{fig:monster-cd}), 0.69 behind, just beyond the Nemenyi critical
difference of 0.65. The margin is narrow for HashBoost: its pairwise
Wilcoxon test against ExtraTrees is not significant ($p = 0.11$, against
$0.031$ for XGBoost), although its error ratio of 0.90 has a 95\% interval of
0.84--0.97 that excludes 1. ExtraTrees' largest losses are on big acoustic
and sensor pools: MosquitoSound (1.52 times HashBoost's error), AudioMNIST-DS,
FruitFlies, Pedestrian, InsectSound and TimeSen2Crop.

\paragraph{Validation error is optimistic.}
Test error is about 3.3 times validation error for all three models. The
validation and tune slices are random draws from the
pool, while the test folds differ from it in distribution. On DREAMERA,
XGBoost's validation error is half HashBoost's (0.071 against 0.135), yet both
are near 0.5 on test. Every model is tuned on the same optimistic slices, so
the comparison stays fair.

\subsection{Where the time goes (RQ2)}
\label{sec:cost}

\paragraph{The speedup follows XGBoost's cost.}
On the same GPU, HashBoost trained 8.2 times faster than XGBoost in total:
18,214\,s against 149,099\,s over the 130 dataset-folds. The total hides a wide
range. Per dataset, HashBoost is faster on 14 of the 26, with a median speedup
of 1.23, and the range runs from 31 times faster on S2Agri-10pc-34 to 7 times
slower on WISDM. \Cref{fig:monster-speed} (left) shows what decides it. The
speedup rises with $N \cdot p \cdot k$, the rows, features and classes that set
XGBoost's cost per round (Spearman $\rho = 0.87$, $p = 7\times10^{-9}$),
while HashBoost's cost is set by its batch budget. On the cheapest datasets,
such as WISDM, LakeIce and UCIActivity, XGBoost finishes in seconds and
HashBoost's fixed cost per round makes it the slower model. On the most
expensive, S2Agri and TimeSen2Crop, XGBoost takes hours and HashBoost minutes.

\paragraph{HashBoost's budget ran out on the largest pools.}
Run to completion, XGBoost overtakes HashBoost on S2Agri and TimeSen2Crop,
and those are among the datasets where it clearly leads on test. But HashBoost
was stopped by its budget, not by its tune error: it reached its 5,000-batch
cap on 14 of the 15 S2Agri and Traffic folds with its best tune error in the
last 1,000 batches, still improving. On S2Agri-10pc-34 it reached its
tune-chosen point in 375\,s, where XGBoost needed 12,661\,s. A larger budget
would cost minutes, and might close part of that gap.

\paragraph{Memory does not grow with the training set.}
\label{sec:memory}
We streamed LenDB's whole training pool (975,291 rows: 6.3\,GB as raw series
and 58\,GB after QUANT) through both models on the RTX 4060. HashBoost's peak
GPU memory was the same, 2,572\,MB, at 65,536 rows and at the full pool,
because each batch is folded into the tables and freed. XGBoost's binned matrix
grows linearly with the pool, to 14.6\,GB (\cref{fig:scaling}, right). On the
8\,GB card it had to page that matrix from disk every round, at 116\,s per
round against 0.68\,s at 65,536 rows. In the MONSTER benchmark on the L40S,
tuned XGBoost held LenDB's matrix on the card at 17.1--17.8\,GB, against
3.4--4.9\,GB for HashBoost's \code{L}.

\paragraph{Freezing keeps the cost per batch flat.}
Without freezing, per-batch cost grows with rounds: on a streamed Traffic run
it rose from 2\,ms to 14.5\,ms over 2,840 rounds, while a window of one or two
epochs' rounds held it level (\cref{fig:scaling}, left). On Pedestrian, with
two rounds per batch, a window of ten epochs matched the unfrozen model's
accuracy in 2.4 times less time (validation error \pmsd{0.2135}{0.0032} in 10.8\,s against
\pmsd{0.2133}{0.0025} in 25.6\,s, three runs each). Every MONSTER configuration
freezes rounds older than 128 batches.

\subsection{The small-data boundary (RQ3)}
\label{sec:ucr}

On the UCR 112 the training sets are small, and HashBoost loses both its
accuracy and its speed advantage (\cref{tab:ucr}). Our ExtraTrees reproduces the published QUANT
results~\cite{middlehurst2024bakeoff} (mean error 0.1475 against 0.1456), and
it is both the most accurate model, significantly ahead of both boosters
(\cref{fig:ucr-cd}), and the fastest, at 70\,s for all 112 against HashBoost's
183\,s. At these sizes a round's cost is fixed overhead rather than
arithmetic. HashBoost at its MONSTER defaults is level with default XGBoost
(mean ranks 2.36 and 2.39). Its 8-bit rounds were set for buckets that see
thousands of rows, and most UCR training sets cannot fill them. Resized for
small data, with two bits and 3,200 rounds chosen by two-fold
cross-validation over the datasets, HashBoost is significantly ahead of XGBoost
(lower error on 82 datasets, higher on 29, $p = 4.5\times10^{-8}$) and still
behind ExtraTrees (28 against 63, $p = 1.2\times10^{-5}$), at 7.5 times the
time. Which classifier suits QUANT's features therefore depends on scale: an
average of random trees on small training sets, and a booster on large ones.

\section{Discussion}

\paragraph{Speed against accuracy.}
Because the two models' costs scale differently, the speedup is largest where
the classifier's cost was a problem, which is where HashBoost is meant to be
used. There it also gives up the most accuracy once XGBoost has run to
completion (its error is 1.12 times XGBoost's on S2Agri and 1.66 times on
TimeSen2Crop), while being far ahead at equal time. On S2Agri, HashBoost
stopped at its batch budget while still improving, so the trade-off is at
least partly set by a budget tuned on smaller pools rather than by a ceiling
of the model. On TimeSen2Crop it reached the budget on only two folds of
five, so the budget explains less of that gap, the largest in the
benchmark.

\paragraph{Limitations.}
\begin{itemize}
    \item The MONSTER benchmark is one run per test fold. Over five model seeds
          on fold 0, HashBoost's standard deviation was 0.0002 to 0.0024 on
          most datasets.
    \item Both models were tuned for accuracy, not speed, and only on 10 of
          the 26 datasets, which flatter HashBoost (\cref{sec:accuracy}).
    \item The time-matched comparison is on validation error, because test
          error was scored only at each model's own chosen round. XGBoost's
          clock is its build plus its mean time per round.
    \item Configurations were chosen on validation error, which
          underestimates test error about 3.3-fold, so they may not be the
          best on test, for either model.
    \item The UCR results are one run on the default split, where the bake-off
          averages 30 resamples.
    \item The comparison includes XGBoost and ExtraTrees only, not LightGBM or
          CatBoost, and ExtraTrees' CPU time is not directly comparable.
\end{itemize}

\paragraph{Future work.}
The largest datasets suggest that a round budget that grows with the training
pool would buy accuracy for minutes of training. A configuration tuned for
speed rather than accuracy would map the trade-off on the test folds. Choosing
the bit width from the number of rows per class could unify the UCR and
MONSTER settings, and cheaper rounds would help on small datasets, where a
round's cost is fixed overhead.

% ==============================================================================
\section{Conclusion}

Gradient boosting does not need a tree, or a search over the training set,
to be accurate at scale. A global partition placed between hard examples, with
leaves refined by every later mini-batch, matched tuned XGBoost on MONSTER at a
cost set by its own budget rather than by the data. That makes it fastest
where tree boosting is slowest, and the wrong choice on small datasets, where
ExtraTrees is both faster and more accurate.
