\begin{abstract}
    Gradient boosted decision trees are the usual classifier to put on top of
    interval-based time series features, but inducing each tree means searching
    for splits over the whole training set. We replace the tree with a
    \emph{global partition}: $b$ threshold predicates, placed between pairs of
    hard, differently labelled examples, that index a table of $2^b$ leaf
    values. The resulting booster, HashBoost, does no exhaustive split search
    and trains from mini-batches, so its memory use does not depend on the size
    of the training set. We implement it on the GPU in PyTorch and evaluate it
    after a QUANT transform. On all 26 MONSTER datasets, with each model's
    configuration chosen by the same procedure on validation data and frozen
    before testing, HashBoost is level with tuned XGBoost on MONSTER's five
    test folds (error ratio 1.02, Wilcoxon $p = 0.98$) and trains 8.2$\times$
    faster in total on the same GPU. Both boosters rank significantly ahead of
    QUANT's own ExtraTrees classifier there. On the 112 UCR datasets, where
    training sets are small, the order reverses: ExtraTrees is best, and
    HashBoost at its defaults is level with default XGBoost. With fewer bits
    per round and more rounds, HashBoost is significantly ahead of XGBoost.
    HashBoost's limit is the number of rounds it can afford, not memory: every
    batch updates every existing round, so cost is quadratic in rounds, and
    freezing old rounds makes it linear.
\end{abstract}

\section{Introduction}

Gradient boosted models are built from a sequence of decision trees, where each
tree is fitted to the residual errors of the ensemble constructed so far rather
than to the original targets~\cite{friedman2001greedy}. This stage-wise
additive formulation, together with highly engineered implementations such as
XGBoost~\cite{chen2016xgboost}, LightGBM~\cite{ke2017lightgbm} and
CatBoost~\cite{prokhorenkova2018catboost}, has made boosting the default choice
for tabular prediction tasks, where it remains competitive with, and frequently
superior to, deep learning~\cite{shwartzziv2022tabular,grinsztajn2022why}.

Tree ensembles are also the usual classifier on top of interval-based time
series features. QUANT~\cite{dempster2024quant} passes its quantile features to
an ensemble of extremely randomised trees, and the features produced by
PULSAR~\cite{pulsar} and its predecessors are used the same way. At the scale
of the MONSTER benchmark~\cite{dempster2025monstermonashscalabletime}, with up
to 5.9 million series per dataset, the classifier becomes the expensive part.
Inducing a tree requires evaluating candidate split points at every node, so
each boosting iteration costs time proportional to both the number of
instances and the number of features. Histogram binning, approximate split
finding, gradient-based sampling and feature
bundling~\cite{chen2016xgboost,ke2017lightgbm,friedman2002stochastic} all
reduce the constant factor. They do not remove the need to revisit the whole
training set in every round, and in practice to hold it in memory.

This paper asks whether the tree is needed at all. We replace each tree with a
\emph{global partition} of the feature space: $b$ axis-aligned threshold
predicates, applied to every example at once. The resulting $b$ bits index a
table of $2^b$ leaf values. A predicate takes a random feature and puts its
threshold at the midpoint of two hard, differently labelled examples. Each leaf
value is a Newton step computed from running sums of the gradient and hessian
over the examples that land in it. Because the partition does not depend on
which examples are in the current batch, those running sums can be updated
from any later mini-batch, and the model never needs the training set in one
place. We ask three questions:
\begin{description}
    \item[RQ1] Can a booster of global partitions match a boosted tree
               ensemble's accuracy at scale, given the same tuning effort?
    \item[RQ2] What does it cost to train, and how does that cost grow with
               the training set and the number of rounds?
    \item[RQ3] How does it fare on small training sets, against the classifier
               QUANT was designed with?
\end{description}

\paragraph{Contributions.}
\begin{enumerate}
    \item \textbf{HashBoost}, a gradient booster whose weak learner is a global
          partition, and a GPU implementation that agrees with an independent
          CPU reference to $4\times10^{-7}$ (\cref{sec:method}).
    \item \textbf{Round freezing}, which with a per-row cache turns HashBoost's
          quadratic cost in rounds into a linear one (\cref{sec:freezing}).
    \item \textbf{An evaluation on all 26 MONSTER datasets}, trained on whole
          pools of up to 4.65 million rows and scored on MONSTER's five test
          folds, against XGBoost tuned by the same procedure and against
          QUANT's ExtraTrees (\cref{sec:monster}).
    \item \textbf{An evaluation on the 112 UCR datasets} against the same two
          baselines, including how the bit width and round budget should
          change for small training sets (\cref{sec:ucr}).
\end{enumerate}

\section{Background and Related Work}
\label{sec:related}

\paragraph{Boosting.}
Boosting originates in the observation that a set of weak learners can be
combined into an arbitrarily strong one, formalised by
AdaBoost~\cite{freund1997decision} and later generalised to arbitrary
differentiable losses as gradient boosting~\cite{friedman2001greedy}. Decision
trees are the conventional weak learner, but nothing in the gradient boosting
framework requires them. Modern implementations fit each tree to a
second-order expansion of the loss, so that a leaf's value is a Newton step
$-\sum g / \sum h$ over the examples it contains~\cite{chen2016xgboost}.
HashBoost keeps this leaf rule and changes how examples are assigned to
leaves.

\paragraph{Oblivious trees and decision tables.}
CatBoost~\cite{prokhorenkova2018catboost} grows \emph{oblivious} trees, in
which every node at a given depth uses the same split. A depth-$d$ oblivious
tree is therefore $d$ predicates whose outcomes index $2^d$ leaves. This is
the same structure as one HashBoost round, and neural oblivious
ensembles~\cite{popov2020node} use it too. CatBoost chooses each level's split
greedily by gain over the whole training set, and fixes the leaves once the
tree is built. Boosted decision tables~\cite{lou2017bdt} are the closest
relative. They choose a table's tests greedily by squared-error gain over the
whole training set, then \emph{backfit} them: each test is removed and
re-chosen given the others. A table's leaf values are set once, as the mean
target in each partition, and earlier tables are never revisited. HashBoost
does the opposite on both counts. Its tests are not searched for over the
training set, and the leaves of every earlier round are re-estimated by each
later batch. That is closer to backfitting additive
models~\cite{buja1989linear}, applied online, than to backfitting the splits
within one table.

\paragraph{Randomised partitions.}
Random forests~\cite{breiman2001random} and extremely randomised
trees~\cite{geurts2006extremely} showed that much of the split search in a
tree can be replaced by randomness without losing accuracy, provided the
ensemble is large. Extremely randomised trees draw both the feature and the
threshold at random, and QUANT uses them as its
classifier~\cite{dempster2024quant}. A random global partition can also be
read as a locality-sensitive hash~\cite{indyk1998approximate}: examples that
share a code agree on $b$ random comparisons. HashBoost's thresholds are
random but not uninformed. They sit between two hard examples of different
classes, so each bit tends to separate examples the current model confuses.

\paragraph{Time series classification.}
Random-feature methods have shown that the expensive, data-dependent search of
tree induction can often be replaced by cheap, data-independent random
transformations. ROCKET~\cite{dempster2020rocket} applies a large bank of
random convolutional kernels followed by a linear classifier, matching far
more expensive ensembles such as HIVE-COTE~\cite{middlehurst2021hivecote2} at a
small fraction of the cost, and MiniRocket~\cite{dempster2021minirocket} and
Hydra~\cite{dempster2023hydra} refine it. A parallel line of work extracts
features from intervals of the series: Time Series Forest~\cite{deng2013tsf},
CIF~\cite{middlehurst2020cif}, DrCIF~\cite{middlehurst2021hivecote2},
rSTSF~\cite{cabello2021rstsf}, QUANT~\cite{dempster2024quant} and
PULSAR~\cite{pulsar}. All of these end in some form of tree. We use QUANT as a
fixed feature transform and replace only the classifier.

\section{Method}
\label{sec:method}

\subsection{A round is a global partition}

Let $x \in \mathbb{R}^p$ be a feature vector and $k$ the number of classes. A
round $r$ is defined by $b$ pairs $(j_{r,i}, t_{r,i})$ of a feature index and a
threshold, for $i = 0, \dots, b-1$. It maps $x$ to a $b$-bit code
\begin{equation}
    c_r(x) = \sum_{i=0}^{b-1} 2^i \, \mathbb{1}\!\left[x_{j_{r,i}} \le t_{r,i}\right]
    \in \{0, \dots, 2^b - 1\},
\end{equation}
and has a table $L_r \in \mathbb{R}^{2^b \times k}$ of leaf values. The model
after $R$ rounds is
\begin{equation}
    F(x) = \sum_{r=1}^{R} L_r\!\left[c_r(x)\right] \in \mathbb{R}^k,
\end{equation}
and predicts $\mathrm{softmax}(F(x))$. A round is an oblivious tree of depth
$b$ whose splits are fixed when it is created. The default is $b = 8$, so a
round has 256 buckets.

\subsection{Choosing the predicates}

Given the current batch, its probabilities and its labels, a new round's
predicates are chosen as follows:
\begin{enumerate}
    \item Order the batch by cross entropy, hardest first.
    \item Walk that order and greedily form $b$ pairs of examples with
          different labels.
    \item For each pair $(u, v)$, draw a feature $j$ uniformly at random and set
          $t = (u_j + v_j)/2$.
\end{enumerate}
Each bit therefore separates two examples the model currently gets wrong, and
the only search is the sort in the first step. A \emph{gain-selected} variant
draws $K$ such hard-pair candidates per bit and fills the bits one at a time,
as CatBoost grows an oblivious tree: each bit takes the candidate with the
highest second-order gain, $\sum G^2/(H+\epsilon)$, within the cells the
earlier bits have made. It searches only $K$ random candidates per bit, on one
batch.

\subsection{Fitting the leaves}

We use the softmax cross-entropy gradient $g = p - \mathrm{onehot}(y)$ and a
floored diagonal hessian $h = p(1-p) + 10^{-3}$. Every round keeps running sums
$G_r, H_r \in \mathbb{R}^{2^b \times k}$ of $-g$ and $h$ over the examples that
landed in each bucket, and its leaf values are
\begin{equation}
    L_r[s] = \eta \, \frac{G_r[s]}{H_r[s] + \epsilon},
\end{equation}
with learning rate $\eta = 0.1$. By default $\epsilon = 10^{-6}$; a larger
$\epsilon$ is an L2 penalty that shrinks thinly populated leaves.

The key departure from tree boosting is \emph{when} these sums are
accumulated. A tree's leaves are fitted once, when the tree is built, and
never change. In HashBoost, \textbf{every mini-batch is accumulated into every
existing round}, with gradients evaluated at the current model
(\cref{alg:hashboost}). A round created early keeps absorbing evidence from
every batch that follows, so a round is not tied to the batch that created it,
and the model can learn from a stream. It is also where the cost comes from: a
batch costs $O(R)$ once there are $R$ rounds, so $T$ batches with one new round
each cost $O(T^2)$.

\begin{algorithm}[t]
    \caption{One HashBoost step on a mini-batch $(X, y)$ of $n$ examples,
        adding $H$ rounds.}
    \label{alg:hashboost}
    \begin{algorithmic}[1]
        \For{$h = 1, \dots, H$}
        \State $F \gets \sum_{r < R} L_r[c_r(X)]$ \Comment{$(n, k)$ logits}
        \State $p \gets \mathrm{softmax}(F)$;\quad $g \gets p - \mathrm{onehot}(y)$;\quad $h \gets p(1-p) + 10^{-3}$
        \State choose predicates of round $R$ from hard pairs in $(X, y, p)$
        \For{$r = 0, \dots, R$} \Comment{all rounds, including the new one}
        \State $G_r[c_r(X)] \mathrel{+}= -g$;\quad $H_r[c_r(X)] \mathrel{+}= h$ \Comment{scatter-add}
        \State $L_r \gets \eta\, G_r / (H_r + \epsilon)$
        \EndFor
        \State $R \gets R + 1$
        \EndFor
    \end{algorithmic}
\end{algorithm}

\paragraph{Rounds per batch.}
Adding $H > 1$ rounds per batch raises capacity without more passes over the
data. Each of the $H$ steps re-accumulates the batch into the existing rounds.

\paragraph{Round freezing.}
\label{sec:freezing}
With a window of $W$ rounds, only the newest $W$ keep accumulating. Older
rounds are frozen, and a frozen round's contribution to a given example never
changes again. Given stable row ids, each row's frozen contribution is summed
once, cached in an $(N, k)$ table, and never recomputed. A batch then costs
$O(W + f)$, where $f$ is the number of rounds frozen since its rows were last
seen, so total cost becomes linear in rounds.

\subsection{Implementation}
\label{sec:implementation}

HashBoost runs entirely on the GPU in PyTorch. A batch's codes are a
\code{uint8} tensor of shape $(R, n)$, built one bit at a time, so the largest
intermediate is a single gather. $G$ and $H$ share one $(R, 2^b, 2k)$ tensor,
so one \code{scatter\_add\_} updates both. Work is chunked over rounds to a
fixed memory budget, so peak memory does not grow with $R$ beyond the tables
themselves. The original numba CPU implementation is kept as a reference.
Given the same predicates, the two agree to $4\times10^{-7}$ in logits with
identical predictions, and a test suite keeps the defaults equal to it. The
GPU version trains Pedestrian's default 800 rounds in about 7.5\,s, against
101.5\,s for the reference.

\paragraph{Configurations.}
\label{sec:configs}
HashBoost and XGBoost were tuned the same way, on fold 0's validation error
alone. We screened one change at a time on 10 of the 26 datasets
(CrowdSourced, DREAMERA, FordChallenge, InsectSound, LenDB, PAMAP2, STEW,
Traffic, UCIActivity and WISDM), fixed two configurations per model, and ran
both on all 26. For each dataset and model the configuration with the lower
fold-0 tune error was frozen. Each frozen configuration was then trained once
on each of the five folds and scored once on that fold's test series, at the
round its tune error chose. No test series was seen before this.

Both HashBoost configurations train for up to 5,000 batches of 4,096 rows,
evaluate every 50 batches, stop once their best tune evaluation is 1,000
batches old, and freeze rounds older than 128 batches:
\begin{itemize}
    \item \code{G}: 6-bit gain-selected rounds ($K = 64$ candidates per bit),
          $\epsilon = 100$, 8 rounds per batch. Picked on 18 datasets.
    \item \code{L}: 8-bit hard-pair rounds, $\epsilon = 1$, 16 rounds per
          batch. Picked on the largest pools (LenDB, both S2Agri, Traffic,
          Pedestrian), WhaleSounds and the EEG sets DREAMERA and DREAMERV.
\end{itemize}
Over five model seeds on fold 0, the pick was the same every time on 25 of the
26 datasets. XGBoost's screen raised its cap to 5,000 rounds with 100 rounds
of patience, then varied depth, learning rate, subsampling, L2 regularisation
and the number of bins. Its configurations are \code{d4} (depth 4, learning
rate 0.1; picked on 17 datasets) and \code{d8} (depth 8, learning rate 0.05,
64 bins; picked on 9). The third model, ExtraTrees with QUANT's own settings
(200 trees, entropy criterion, a tenth of the features per split), chooses
nothing after training, so it trains on the same rows and needs no tune slice.

\paragraph{UCR.}
We also use the 112 univariate UCR datasets~\cite{dau2019ucr} with equal
lengths and no missing values that the bake-off reports
on~\cite{middlehurst2024bakeoff}, less Fungi, which has one training series
per class. Each uses the archive's default train/test split. The training sets
are small: 16 to 8,926 series (median 190), and only 11 have 1,000 or more.
UCR has no validation split, so every model runs at fixed settings, nothing is
chosen after training, and we report test error. The baselines are ExtraTrees
with QUANT's settings and XGBoost at its library defaults (100 rounds,
learning rate 0.3, depth 6). HashBoost's default budget is 800 rounds of 8
bits, cycling batches of at most 4,096 rows.

\paragraph{Hardware and noise.}
The MONSTER boosting runs each ran alone on one NVIDIA L40S (46\,GB) on
Monash's M3 cluster, and ExtraTrees on CPU nodes with 36 cores. UCR and the
streaming and freezing runs in \cref{sec:scaling} used one RTX 4060 (8\,GB).
Seeding does not
make HashBoost reproducible: float32 scatter-adds on the GPU accumulate in a
nondeterministic order, and the perturbation grows through the ranking that
chooses predicates. On Pedestrian the run-to-run standard deviation of
validation error is about 0.003, so gaps under about 0.006 there are not
treated as results.

\paragraph{HashBoost and tuned XGBoost are level.}

\subsection{Cost and scaling (RQ2)}
\label{sec:scaling}

\paragraph{Training time on MONSTER.}
On the same GPU, HashBoost trained 8.2 times faster than XGBoost in total:
18,214\,s against 149,099\,s over the 130 dataset-folds, or 3.9 times
without S2Agri, where XGBoost spent 92,001\,s. On small pools XGBoost is
faster, because HashBoost's cost per round is mostly fixed: UCIActivity took
169\,s against 46\,s. \Cref{fig:monster-time} shows where the time goes on the
six largest pools. On S2Agri-10pc-34, HashBoost reaches its tune-chosen point
(validation error 0.0200) after 375\,s and XGBoost reaches its point (0.0166)
after 12,661\,s. On TimeSen2Crop the times are 398\,s and 5,256\,s. There
XGBoost's extra hours buy its accuracy lead, but HashBoost was also stopped by
its budget: it reached 5,000 batches on 14 of the 15 S2Agri and Traffic folds
with its best tune error in the last 1,000 batches, still improving. On
Traffic and Pedestrian its curve is at or below XGBoost's throughout.

\paragraph{Memory does not grow with the training set.}
We streamed LenDB's whole training pool (975,291 rows: 6.3\,GB as raw series

validation rows as a 65,536-row run. HashBoost's peak GPU memory was the same
at both sizes, 2,572\,MB, because each batch is folded into the tables and
freed. XGBoost's binned matrix is one byte per row and feature and grows
linearly (\cref{fig:scaling}, right): 14.6\,GB at the full pool, which it paged from disk every round at
116\,s per round against 0.68\,s at 65,536 rows. On the L40S in the MONSTER
benchmark, tuned XGBoost held LenDB's matrix on the card at 17.1--17.8\,GB,
against 3.4--4.9\,GB for HashBoost's \code{L}.

\paragraph{More data needs more rounds.}
With the default single round per batch, the whole-pool model was
\emph{worse} than the 65,536-row model at the same 1,200 rounds (validation
error 0.0691 against 0.0532). It was underfitting, with a training error of
0.0608, while the small model had memorised its rows (0.0049). With 16 rounds
per batch and freezing, \code{L} reaches \pmsd{0.0428}{0.0018} over five
seeds on the whole pool, ahead of both. HashBoost's scaling is limited by
rounds, not memory, and the quadratic cost is what makes rounds expensive.

\paragraph{Freezing makes the cost linear.}
Per-batch cost grows with the number of rounds: on a streamed Traffic run it
rose from 2\,ms to 14.5\,ms over 2,840 rounds, while a window of one or two
epochs' rounds levels it off (\cref{fig:scaling}, left), and 1,600 rounds on Pedestrian
took 37.5\,s against 10.5\,s for 800. \Cref{tab:frozen} shows freezing on
Pedestrian. A window of ten epochs' rounds matches 1,600 unfrozen rounds'
accuracy in 2.4 times less time. The window matters: two epochs cost up to
0.027 on Pedestrian, but nothing measurable on InsectSound or on whole-pool
Traffic and LenDB. Every configuration in \cref{sec:monster} freezes rounds
older than 128 batches.

\subsection{Random partitions, and when to inform them}
\label{sec:negative}

In development at 65,536 rows, nearly every change that made an individual
round better informed made the ensemble worse. Choosing each round's
predicates by gain raised the number of occupied buckets from 79 to 119 of
256 on Pedestrian, and left the error the same or worse. The same went for richer QUANT features,
feature filtering and oblique predicates. The randomness of the predicates
appears to be what makes rounds diverse enough to add up, as in extremely
randomised trees~\cite{geurts2006extremely}. The exception came on whole
MONSTER pools, where gain selection over 64 candidates, with 6-bit rounds and
a heavy leaf penalty ($\epsilon = 100$), was the largest single gain in the
screen: it cut CrowdSourced's validation error from 0.042 to 0.006 and
FordChallenge's from 0.105 to 0.062. This became \code{G}. The penalty appears
to be what lets gain-chosen rounds generalise, and where it does not
(the largest pools and the EEG sets), the random \code{L} is picked instead.

\section{Discussion}

\paragraph{Can the tree be replaced? (RQ1, RQ3)}
At MONSTER's scale, yes. With both boosters tuned the same way and scored on
the five test folds, HashBoost is level with XGBoost across all 26 datasets.
On the 112 small UCR datasets it is level with default XGBoost at its own
defaults, and ahead with fewer bits and more rounds. Neither booster is the
best classifier for QUANT's features everywhere: ExtraTrees wins on UCR and
loses on MONSTER. On small training sets an average of random trees wins, and
on large ones a booster wins, whether its weak learner is a tree or a global
partition.

\paragraph{What does it cost? (RQ2)}
HashBoost's memory use is independent of the training set, so it trains on
whole pools of millions of rows on a single GPU, at an eighth of tuned
XGBoost's total time on MONSTER. Its binding constraint is the number of
rounds. Freezing removes the quadratic growth, but the round budget still
limited it on the largest pools.

\paragraph{Limitations.}
\begin{itemize}
    \item The MONSTER benchmark is one run per test fold. Over five model seeds
          on fold 0, HashBoost's standard deviation was 0.0002 to 0.0024 on
          most datasets.
    \item Both models' configurations were chosen on 10 of the 26 MONSTER
          datasets, where HashBoost had also been developed for longer, and it
          does better there.
    \item HashBoost's budget of 5,000 batches stopped it while it was still
          improving on S2Agri and Traffic. A budget scaled with the pool might
          narrow its deficit on S2Agri; it was not tried, to keep the
          configurations frozen.
    \item On MONSTER, validation error underestimates test error about
          3.3-fold, so configurations chosen on validation may not be the best
          on test, for either model.
    \item The UCR results are one run on the default split, where the bake-off
          averages 30 resamples, and its baselines are at fixed library
          settings. The bits-and-rounds choice never reads the test sets it is
          scored on, but it does read the other half's.
    \item The final comparison includes XGBoost and ExtraTrees only, not
          LightGBM or CatBoost. ExtraTrees ran on CPUs, so its time is not
          directly comparable.
\end{itemize}

\paragraph{Future work.}
A round budget that scales with the training set; a bit width chosen per
dataset from its rows per class, which would unify the UCR and MONSTER
settings; cheaper rounds on small datasets, where a round's cost is fixed
overhead; and understanding the chaotic leaf dynamics that set HashBoost's
run-to-run noise.

\section{Conclusion}

HashBoost replaces the decision tree in gradient boosting with a global
partition: $b$ threshold predicates, placed between pairs of hard examples,
that index a table of Newton-step leaves refined by every later mini-batch. It
never holds the training set. On all 26 MONSTER datasets, scored on the five
test folds, it is level with XGBoost tuned by the same procedure and trains
8.2 times faster on the same GPU, and both rank significantly ahead of QUANT's
ExtraTrees. On the small UCR datasets, with fewer bits and more rounds, it is
significantly ahead of XGBoost and behind ExtraTrees. What limits it is the
number of rounds it can afford, which round freezing makes linear in cost.
