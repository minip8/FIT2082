\begin{abstract}
    On large time series datasets, the classifier becomes the expensive part
    of the pipeline. A boosted tree ensemble such as XGBoost searches every
    feature for splits in every round and keeps the whole training set in
    memory. We replace each tree with a \emph{global partition}: a few
    thresholds, each placed between two hard examples of different classes,
    whose bits index a table of leaf values. The resulting booster, HashBoost,
    trains from mini-batches on the GPU, at a cost set by its round budget
    rather than by the size of the data. On the 26 MONSTER datasets with QUANT
    features, it matches tuned XGBoost's test accuracy and trains 8.2$\times$
    faster in total on the same GPU, up to 31$\times$ on the largest datasets,
    though it is slower on the cheapest. On the small datasets of the UCR
    archive the advantage disappears, and QUANT's own ExtraTrees classifier is
    both faster and more accurate.
\end{abstract}

\section{Introduction}

Gradient boosted decision trees~\cite{friedman2001greedy}, in implementations
such as XGBoost~\cite{chen2016xgboost}, LightGBM~\cite{ke2017lightgbm} and
CatBoost~\cite{prokhorenkova2018catboost}, are the default choice for tabular
prediction, where they remain competitive with, and frequently superior to,
deep learning~\cite{shwartzziv2022tabular,grinsztajn2022why}. Tree ensembles
are also the usual classifier on top of interval-based time series features:
QUANT~\cite{dempster2024quant} passes its quantile features to extremely
randomised trees, and PULSAR~\cite{pulsar} is used the same way.

At the scale of the MONSTER
benchmark~\cite{dempster2025monstermonashscalabletime}, with up to 5.9 million
series per dataset and tens of thousands of features after QUANT, the
classifier becomes the expensive part. To grow a boosted tree, the learner
searches for split points on every feature, and a multiclass booster grows one
tree per class in every round. The cost of a round is therefore proportional
to the number of rows, features and classes multiplied together. Histogram
binning, approximate split finding, gradient-based sampling and feature
bundling~\cite{chen2016xgboost,ke2017lightgbm,friedman2002stochastic} all
reduce the constant factor, but every round still has to revisit the whole
training set, and the training set has to be held in memory.

In this paper we replace each tree with a \emph{global partition} of the
feature space. A partition is $b$ axis-aligned threshold predicates, applied
to every example at once, and their $b$ bits index a table of $2^b$ leaf
values. Each predicate takes a random feature and puts its threshold halfway
between two hard examples with different labels, so no search over the
training set is needed. The partition also does not depend on which examples
happen to be in the current batch. Its leaf values can be re-estimated from
any later mini-batch, and the model never needs the whole training set in
memory at once. Since nothing in a round depends on the size of the training
set, HashBoost's cost stays flat on exactly the datasets where boosted trees
become expensive. We ask three questions:
\begin{description}
    \item[RQ1] Given the same tuning effort, does HashBoost match a tuned
          boosted tree ensemble's accuracy on MONSTER's test folds?
    \item[RQ2] How much faster is HashBoost, on which datasets, and why? What does
          each model reach in the same training time, and what memory
          does each need?
    \item[RQ3] Where does the advantage stop? Does it hold on small
          training sets?
\end{description}

\Cref{sec:method} describes HashBoost and its GPU implementation. We then
compare it against XGBoost, tuned by the same procedure, and against QUANT's
ExtraTrees on all 26 MONSTER datasets, training on whole pools of up to 4.65
million rows. \Cref{sec:accuracy} answers RQ1, \cref{sec:cost} explains where
the time goes, and \cref{sec:ucr} tests the small-data boundary on the 112
UCR datasets. Our code is available at
\url{https://github.com/minip8/FIT2082}.

\section{Background and Related Work}
\label{sec:related}

HashBoost is a gradient booster~\cite{freund1997decision,friedman2001greedy}
with a different weak learner. Trees are the usual choice, but nothing in the
framework requires them. From XGBoost~\cite{chen2016xgboost} HashBoost keeps
the second-order leaf rule, in which a leaf's value is a Newton step
$-\sum g / \sum h$ over its examples, and it changes only how examples are
assigned to leaves. Its closest relatives restrict the shape of the tree.
CatBoost~\cite{prokhorenkova2018catboost} grows \emph{oblivious} trees, which
use the same split at every node of a given depth, so a depth-$d$ tree is
$d$ predicates indexing $2^d$ leaves, the same structure as one HashBoost
round. Boosted decision tables~\cite{lou2017bdt} are closer still. Like
CatBoost, they choose each test greedily by gain over the whole training set,
and then \emph{backfit} them, re-choosing each test given the others. They
set each table's leaves once. HashBoost does the opposite on both counts. Its
tests are never searched for over the training set, and every new batch
re-estimates the leaves of every earlier round, which is closer to
backfitting in additive models~\cite{buja1989linear}, done online.

Random forests~\cite{breiman2001random} and extremely randomised
trees~\cite{geurts2006extremely} showed that a large enough ensemble can
replace much of the split search with randomness. HashBoost's thresholds are
random too, but each one sits between two hard examples of different
classes, so a bit tends to separate examples that the model is currently
confusing. The usual way to scale tree boosting, though, is to keep the
search and make it faster. GPU histogram
construction~\cite{mitchell2017accelerating} builds each tree's histograms in
parallel, and out-of-core training~\cite{chen2016xgboost} pages the binned
matrix in from disk, but both still pass over the whole training set in
every round. Streaming methods avoid that pass. Hoeffding
trees~\cite{domingos2000mining} grow a single tree from a stream, splitting a
leaf once enough examples have arrived, and online
boosting~\cite{oza2001online,beygelzimer2015online} updates every weak
learner as each example arrives. HashBoost updates all of its learners from
each batch in the same way, but because their structure is fixed when they
are created, an update is a scatter-add rather than a refit.

In time series classification, random-feature methods have shown that
data-dependent search can often be replaced by cheap random transformations.
ROCKET~\cite{dempster2020rocket},
MiniRocket~\cite{dempster2021minirocket} and Hydra~\cite{dempster2023hydra}
pair random convolutional kernels with a linear classifier, at a fraction of
the cost of ensembles such as HIVE-COTE~\cite{middlehurst2021hivecote2}.
Interval methods (Time Series Forest~\cite{deng2013tsf},
CIF~\cite{middlehurst2020cif}, DrCIF~\cite{middlehurst2021hivecote2},
rSTSF~\cite{cabello2021rstsf}, QUANT~\cite{dempster2024quant},
PULSAR~\cite{pulsar}) all finish with some kind of tree. We keep QUANT as a
fixed transform and replace only the classifier.

\section{Method}
\label{sec:method}

HashBoost fixes each weak learner's structure as soon as it is created,
cheaply and without looking at the whole training set, and then lets its
leaf values keep improving as more data passes through. A single random
partition is a weak classifier, but a boosted sum of many, each aimed at the
examples the model currently gets wrong, can be a strong one.

\subsection{A round is a global partition}

Let $x \in \mathbb{R}^p$ be a feature vector and $k$ the number of classes. A
round $r$ is defined by $b$ pairs $(j_{r,i}, t_{r,i})$ of a feature index and a
threshold, for $i = 0, \dots, b-1$. It maps $x$ to a $b$-bit code
\begin{equation}
    c_r(x) = \sum_{i=0}^{b-1} 2^i \, \mathbb{1}\!\left[x_{j_{r,i}} \le t_{r,i}\right]
    \in \{0, \dots, 2^b - 1\},
\end{equation}
and has a table $L_r \in \mathbb{R}^{2^b \times k}$ of leaf values. The model
after $R$ rounds is
\begin{equation}
    F(x) = \sum_{r=1}^{R} L_r\!\left[c_r(x)\right] \in \mathbb{R}^k,
\end{equation}
and predicts $\mathrm{softmax}(F(x))$. A round is thus an oblivious tree of
depth $b$ whose splits are fixed when it is created. By default $b = 8$,
which gives each round 256 buckets.

\subsection{Choosing the predicates}

Given the current batch, its labels and the model's predicted probabilities,
a new round's predicates are chosen as follows:
\begin{enumerate}
    \item Order the batch by cross entropy, hardest first.
    \item Walk that order and greedily form $b$ pairs of examples with
          different labels.
    \item For each pair $(u, v)$, draw a feature $j$ uniformly at random and set
          $t = (u_j + v_j)/2$.
\end{enumerate}
Each bit separates two examples that the model currently gets wrong, and the
only search involved is the sort in the first step. We also use a
\emph{gain-selected} variant. It draws a pool of $bK$ hard-pair candidates
and fills the bits one at a time, much as CatBoost grows an oblivious tree
level by level (\cref{sec:related}). Each bit takes the unused candidate with
the highest second-order gain, $\sum G^2/(H+\lambda)$ with $\lambda = 1$,
summed over classes and over the cells made by the earlier bits, where $G$
and $H$ are the batch's gradient and hessian summed within a cell. The
difference from CatBoost is that HashBoost scores only these $bK$ random
candidates, on a single batch, instead of every feature over the whole
training set.

\subsection{Fitting the leaves}
\label{sec:leaves}

We use the softmax cross-entropy gradient $g = p - \mathrm{onehot}(y)$ and a
floored diagonal hessian $h = p(1-p) + 10^{-3}$. Every round keeps running sums
$G_r, H_r \in \mathbb{R}^{2^b \times k}$ of $-g$ and $h$ over the examples that
landed in each bucket, and its leaf values are
\begin{equation}
    L_r[s] = \eta \, \frac{G_r[s]}{H_r[s] + \epsilon},
\end{equation}
with learning rate $\eta = 0.1$. By default $\epsilon = 10^{-6}$; a larger
$\epsilon$ is an L2 penalty that shrinks thinly populated leaves.

The main departure from tree boosting is \emph{when} these sums are
accumulated. In traditional boosting, a tree is frozen once it is fitted. In
HashBoost, every mini-batch is accumulated into every existing round, with
gradients evaluated at the current model (\cref{alg:hashboost}). A round
created early keeps absorbing evidence from all the batches that follow, so
it is not tied to the batch that created it, and the model can learn from a
stream. Adding $M > 1$ rounds per batch raises capacity without needing more
passes over the data.

\begin{algorithm}[t]
    \caption{One HashBoost step on a mini-batch $(X, y)$ of $n$ examples,
        adding $M$ rounds.}
    \label{alg:hashboost}
    \begin{algorithmic}[1]
        \For{$m = 1, \dots, M$}
        \State $F \gets \sum_{r=1}^{R} L_r[c_r(X)]$ \Comment{$(n, k)$ logits}
        \State $p \gets \mathrm{softmax}(F)$;\quad $g \gets p - \mathrm{onehot}(y)$;\quad $h \gets p(1-p) + 10^{-3}$
        \State choose predicates of round $R+1$ from hard pairs in $(X, y, p)$
        \For{$r = 1, \dots, R+1$} \Comment{all rounds, including the new one}
        \State $G_r[c_r(X)] \mathrel{+}= -g$;\quad $H_r[c_r(X)] \mathrel{+}= h$ \Comment{scatter-add}
        \State $L_r \gets \eta\, G_r / (H_r + \epsilon)$
        \EndFor
        \State $R \gets R + 1$
        \EndFor
    \end{algorithmic}
\end{algorithm}

\subsection{What training costs}
\label{sec:freezing}

A batch of $n$ rows costs one encoding and one scatter-add for each round it
touches, $O(nRb + nRk)$, plus the cost of choosing its new predicates from
that batch alone. None of this depends on the size $N$ of the training pool.
The total cost is the number of batches times the cost per batch, and memory
only has to hold one batch and the tables. A boosted tree's round, by
contrast, builds feature histograms over all $N$ rows for each of the $k$
class trees. Its cost per round grows with $N \cdot p \cdot k$, and it needs
the binned matrix of all $N \times p$ values.

HashBoost does have a scaling problem of its own. Since every batch updates
every round, a batch costs $O(R)$ once there are $R$ rounds, and $T$ batches
cost $O(T^2)$. \emph{Round freezing} removes this growth. With a window of
$W$ rounds, only the newest $W$ keep accumulating, and once a round is frozen
its contribution to an example never changes. Given stable row ids, we can
sum each row's frozen contribution once and cache it in an $(N, k)$ table. A
batch then costs $O(W + f)$, where $f$ is the number of rounds frozen since
its rows were last seen, and the total cost becomes linear in the number of
rounds.

\subsection{Implementation}
\label{sec:implementation}

HashBoost runs entirely on the GPU in PyTorch, as does our port of the QUANT
transform, so features are computed right next to the model that trains on
them. Our first version, a CPU prototype in numba about 13$\times$ slower,
is kept as a test oracle.

\paragraph{Configurations.}
We tuned HashBoost and XGBoost in the same way, on fold 0's validation error
alone. We screened one change at a time on 10 of the 26 datasets
(CrowdSourced, DREAMERA, FordChallenge, InsectSound, LenDB, PAMAP2, STEW,
Traffic, UCIActivity and WISDM), kept two configurations per model, and ran
both on all 26. For each dataset and model we froze the one with the lower
fold-0 tune error, then trained it once on each of the five folds and scored
it once on that fold's test series, at the round its tune error chose. No
test series was seen before then.

\Cref{tab:configs} gives the two HashBoost configurations. Both train on
batches of 4,096 rows for at most 5,000 batches, evaluate every 50, stop once
their best tune evaluation is 1,000 batches old, and freeze rounds older than
128 batches. Over five model seeds on fold 0, the same configuration won
every time on 25 of the 26 datasets.

Our main baseline is XGBoost, tuned with the same effort. We chose it because

because it can train out of core (\cref{sec:memory}). Its screen first raised
the cap to 5,000 rounds with 100 rounds of patience, and then varied depth,

datasets) and \code{d8} (depth 8, learning rate 0.05, 64 bins; picked on 9).
We also compare against ExtraTrees with QUANT's own settings (200 trees,
entropy criterion, a tenth of the features per split).

\paragraph{UCR.}
For smaller datasets, we use the 112 univariate UCR
datasets~\cite{dau2019ucr} reported on by the
bake-off~\cite{middlehurst2024bakeoff}. These are the archive's 128 datasets,
minus the 15 with missing values or unequal lengths, and minus Fungi, which
has only one training series per class. We use each on its default
train/test split, and the training sets range from 16 to 8,926 series
(median 190). Since there is no validation split, every model runs at fixed
settings and we report test error. HashBoost uses 800 rounds of 8 bits,
ExtraTrees uses QUANT's settings, and XGBoost uses its library defaults (100
rounds, learning rate 0.3, depth 6).

\paragraph{Hardware and timing.}
Every HashBoost and XGBoost run on MONSTER had one NVIDIA L40S (46\,GB) on
Monash's M3 cluster to itself, so their times can be compared directly.
ExtraTrees ran on CPU nodes with 36 cores. All reported times include the
QUANT transform. The UCR runs and the streaming runs in \cref{sec:memory}
used one RTX 4060 (8\,GB), with ExtraTrees on the same machine's 12-thread
CPU. Seeding does not make HashBoost deterministic, because scatter-adds on
the GPU accumulate in a nondeterministic order.

\subsection{Where the time goes (RQ2)}
\label{sec:cost}

\paragraph{Training time.}
On the same GPU, HashBoost trained 8.2 times faster than XGBoost in total
(\cref{tab:monster}), but that total hides a wide range. HashBoost is faster
on 14 of the 26 datasets, ranging from 31 times faster on S2Agri-10pc-34 to 7
times slower on WISDM. \Cref{fig:monster-speed} (left) shows what decides
this. The speedup rises with $N \cdot p \cdot k$, the product of rows,
features and classes that sets XGBoost's cost per round (Spearman $\rho =
0.87$), whereas HashBoost's cost is set by its batch budget. On the cheapest
datasets, such as WISDM, LakeIce and UCIActivity, XGBoost finishes in seconds,
and HashBoost's fixed cost per round makes it the slower of the two. On the
most expensive ones, S2Agri and TimeSen2Crop, XGBoost takes hours while
HashBoost takes minutes.

difference is not significant (Wilcoxon $p = 0.24$), because on the cheaper
datasets XGBoost finishes within HashBoost's time anyway. Where training is
expensive, however, the gap is large. Given HashBoost's time, XGBoost only
reaches 0.27--0.29 on the two S2Agri subsets, against HashBoost's 0.02--0.03,
and the gap on TimeSen2Crop is similar. \Cref{fig:monster-time} shows the
curves for the six largest pools.

\paragraph{Memory.}
\label{sec:memory}
HashBoost's memory does not grow with the training set. To show this, we
streamed LenDB's whole training pool (975,291 rows, which is 6.3\,GB as
raw series and 58\,GB after QUANT) through both models on the RTX 4060.
HashBoost's peak GPU memory was 2,572\,MB both at 65,536 rows and at the full
pool, because each batch is folded into the tables and then freed. XGBoost's
binned matrix grows linearly with the pool, reaching 14.6\,GB
(\cref{fig:scaling}, right). On the 8\,GB card, XGBoost had to page that
matrix in from disk every round, which took 116\,s per round, compared with
0.68\,s at 65,536 rows. In the MONSTER benchmark on the L40S, tuned XGBoost
used about 17\,GB of GPU memory on LenDB, while HashBoost used at most
4.9\,GB.

\paragraph{Round freezing.}
Without freezing, the cost per batch grows with the number of rounds. On a
streamed Traffic run it rose from 2\,ms to 14.5\,ms over 2,840 rounds,
whereas a window of one or two epochs' worth of rounds kept it level
(\cref{fig:scaling}, left). On Pedestrian, with two rounds per batch, a
window of ten epochs matched the unfrozen model's validation error in 2.4
times less time.

\subsection{The small-data boundary (RQ3)}
\label{sec:ucr}

The UCR 112 training sets are small, and on them HashBoost loses both its
accuracy and its speed advantage (\cref{tab:ucr}). Our ExtraTrees reproduces
the published QUANT results~\cite{middlehurst2024bakeoff}. It is the most
accurate model, significantly ahead of both boosters (\cref{fig:ucr-cd}), and
also the fastest, taking under half of HashBoost's time. At these sizes, most
of a round's cost is fixed overhead rather than arithmetic. With its MONSTER
defaults, HashBoost is level with default XGBoost. Its 8-bit rounds were set
for buckets that see thousands of rows, and most UCR training sets are too
small to fill them. When we resize it for small data, using two bits and
3,200 rounds chosen by two-fold cross-validation over the datasets, HashBoost
is significantly ahead of XGBoost (lower error on 82 datasets against 29),
but still behind ExtraTrees (28 against 63), and it takes 7.5 times its
default training time. So the best classifier for QUANT's features depends
on scale. An average of random trees works best on small training sets, and
a booster works best on large ones.

\section{Discussion}
\label{sec:discussion}

HashBoost's speedups and its losses fall on the same datasets. Because the
two models' costs scale differently, HashBoost is fastest where the
classifier's cost is a problem in the first place, which is where it is
meant to be used. But on those datasets, once XGBoost has run to completion,
it overtakes HashBoost: HashBoost's error is 1.12 times XGBoost's on S2Agri
and 1.66 times on TimeSen2Crop, even though it is far ahead at equal time.
On S2Agri at least part of that gap comes from the budget rather than from
the model. On 14 of the 15 S2Agri and Traffic folds, HashBoost hit its
5,000-batch cap with its best tune error in the last 1,000 batches, so it
was still improving when it stopped, and that budget had been tuned on
smaller pools. TimeSen2Crop is harder to explain away. There HashBoost hit
the cap on only two of the five folds, and the gap is the largest in the
benchmark.

Tuning also showed us what HashBoost needs. On the smaller pools the random
choice of feature for each predicate held it back, and scoring candidates by
gain was the biggest single improvement we found. Gain selection overfits
the largest pools, however, because each split is the best of hundreds of
candidates on one 4,096-row batch and so can fit that batch's noise. That is
why two configurations survived (\cref{tab:configs}): gain-selected rounds
for most datasets, and plain hard pairs for the largest pools and a few
others. We also tested
whether short freezing windows would regularise the model. They did not, and
freezing is useful only for speed.

\paragraph{Limitations.}
The evidence is thin in three places. First, each result is a single run.
MONSTER has one run per test fold, although over five model seeds on fold 0
HashBoost's standard deviation was 0.0002 to 0.0024 on most datasets, and
the UCR results are one run on the default split, where the bake-off
averages 30 resamples. Second, the tuning. Both models were tuned for
accuracy rather than speed, and only on 10 of the 26 datasets, which flatter
HashBoost (\cref{sec:accuracy}). Validation error was also optimistic: for
all three models, test error is about 3.3 times validation error, because
the test folds are distributed differently from the pool that the
validation and tune slices are drawn from. Every model was tuned on the same
slices, so the comparison stays fair, but configurations chosen on
validation error may not be the best on test. The time-matched comparison
also uses validation error, since test error was scored only at each
model's chosen round, and XGBoost's clock there is its build plus its mean
time per round. Third, we compared against XGBoost and ExtraTrees only, not
LightGBM or CatBoost.

Several directions follow. A round budget that grows with the training pool
should buy accuracy on the largest datasets for a few more minutes of
training, and a configuration tuned for speed would show the trade-off on
the test folds. On small data, choosing the bit width from the number of
rows per class might unify the UCR and MONSTER settings, and cheaper rounds
would cut HashBoost's fixed overhead.

\section{Conclusion}

HashBoost shows that gradient boosting can match tuned XGBoost at scale
without growing trees or searching the training set. It suits large
training pools, where XGBoost's cost per round is the bottleneck, and it is
the wrong choice on small datasets, where ExtraTrees is both faster and more
accurate. The open question is how much of the remaining gap on the very
largest datasets a budget that grows with the pool can close.
